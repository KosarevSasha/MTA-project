# [T024] Настроить миграции для БД
- приоритет: высокий
- статус: открыто
- теги: db, migrations, infra

## Описание
Схема БД сейчас задаётся двумя отдельными SQL-файлами (`mta_schema.sql`, затем `mta_errors.sql`), которые нужно применять вручную и в строго определённом порядке (`sqlite3 mta.db < ...`). Версия схемы нигде не хранится, поэтому нельзя понять, какие изменения применены к конкретной базе, а изменения структуры (например, новые колонки для расхождения остатков из T001 или перенос состояния сессий в БД из T007) придётся вносить вручную.

Что сделать:
- выбрать механизм миграций. Варианты: свой минимальный раннер (таблица `schema_migrations` и нумерованные `.sql`-файлы `migrations/0001_init.sql`, `0002_device_errors.sql`, ...) или готовый инструмент (alembic, yoyo-migrations). Учесть, что зависимостей в проекте мало, а SQLite требует осторожности с `ALTER TABLE`;
- превратить текущие `mta_schema.sql` и `mta_errors.sql` в первые миграции, сохранив результат идентичным;
- обеспечить применение миграций в транзакции и идемпотентность (повторный запуск ничего не меняет);
- добавить команду запуска (например, `uv run python -m mta_project.migrate`) и вызов при инициализации БД; согласовать с T011 (скрипт создания БД) и T014 (включение WAL при инициализации);
- описать в README, как создать новую базу и как обновить существующую, включая уже развёрнутую `mta.db` без таблицы версий (нужен способ «пометить текущее состояние как версию 2»);
- добавить тест: пустая база после всех миграций совпадает по схеме с ожидаемой (см. T023).

Критерий готовности: новая база создаётся одной командой, существующая обновляется без потери данных, текущая версия схемы видна в таблице `schema_migrations`.
